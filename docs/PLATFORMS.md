# Platform support

| Capability | Windows x64 | Linux |
| --- | --- | --- |
| Light/dark controls, Help | Native, custom chrome (egui) | Same chrome and Help; the home page is the stereo viewer |
| Tray / menu | Windows notification icon, jump list | No tray icon yet (planned: StatusNotifier where the desktop supports it); Minimize and Close act normally |
| Ordinary 2D → AI depth | Installed Samsung engine, live on the whole desktop | An open model (Depth Anything V2 Small, Apache-2.0) through the system's ONNX Runtime, then left and right views rendered from the depth map; depth strength and pop-out as on Windows. For still images, and (experimental) for one live screen shown on the Odyssey 3D, with sharpness, depth steadiness and detail controls. Needs `onnxruntime-cpu` or `onnxruntime-cuda` and `any2odyssey --install-depth-model`. The model in the data folder is checked against a fixed SHA-256 before it is loaded, and another file there is refused; a model of your own is named in `$ANY2ODYSSEY_DEPTH_MODEL` |
| Existing SBS input | Samsung/Leia calibrated output | Stereo viewer: an SBS image as red/cyan anaglyph or SBS, half-width stretch, eye swap, preview, output window with full screen, PNG export. Images of up to 16384 pixels a side and 67 million pixels (a side-by-side pair of 8K views fits); larger ones are refused |
| G90XF tracking, calibration and lens output | Samsung/Leia runtime required | Experimental, two ways. (1) "Odyssey 3D": the pair is handed to Leia's own weaver, running with Leia's service and eye tracker from the user's copy of the Windows SR runtime under Wine (`contrib/wine-lens`, `docs/LENS-SWITCH.md`). This needs a Windows installation of the Odyssey 3D Hub that has run this monitor, on a drive Linux can mount: a dual-boot PC is the expected set-up: factory calibration and eye tracking, full screen on the Odyssey. (2) A two-view lens interleave of our own (`core::weave`) with a calibration pattern and three numbers the user tunes (pitch, slant, offset), full screen only, no eye tracking, no use of Samsung's or Leia's calibration files. The lens is asked for while that output is full screen, through an optional helper (`docs/LENS-SWITCH.md`): either Leia's SR runtime for Linux (commercial, not public, untested) or the user's own copy of Leia's Windows runtime under Wine (`contrib/wine-lens`, seen working on a G90XF). Without a helper the lens stays off |
| Whole-desktop source | Windows Graphics Capture | Experimental: one screen, chosen in the desktop's screen-cast portal dialog (PipeWire), shown in 3D on the Odyssey. It needs a desktop whose portal can share a screen: KDE Plasma, GNOME, COSMIC, niri, Hyprland and the wlroots desktops (sway, labwc, river, Wayfire) each have a portal backend for it. An X11 session of Xfce, i3 and the like has none (the GTK backend has file dialogs and no screen cast), and the page says so. On KDE Plasma 6 it can be the Odyssey's own screen (KWin keeps the 3D picture out of the capture); elsewhere it has to be another screen, and the page says that while the screen shows |
| Selected / follow-active window | DWM thumbnails | Not planned |
| Click-through output | Win32 layered + transparent styles | No: the output is an ordinary window you place and make full screen, except the Odyssey 3D picture of a live screen, which lets clicks through |
| Global shortcuts, automatic start, recovery | Yes | Local shortcuts (Ctrl+Alt+F10 output, F1 Help, F11/Esc in the output window), and, when **Global shortcuts** is ticked, five through the desktop's portal where it has them (KDE Plasma 6): output, depth and pop-out, Ctrl+Shift+1 and 3 to 6 unless the desktop gives other keys. Seen in a headless Plasma 6.8 session; the keys themselves are not pressed yet. Output starts manually |
| One instance, `--show` / `--quit` | Named mutex and events | A Unix socket in `$XDG_RUNTIME_DIR`, or in the data folder where that is not set or cannot be used; a second launch hands over its request or file. `--toggle` switches the Windows conversion and is refused here (exit 1) |
| Update check | GitHub Releases, on request or daily | No |
| Installer | Version-aware PowerShell installer | Per release, an Arch Linux package (`packaging/arch/PKGBUILD`, with `any2odyssey-setup`) and an archive with `install.sh` (`packaging/linux/install.sh`); see below |

## What is distributed

- Windows x64, two files per release (built by the release workflow on `windows-latest`, each with a `.sha256`): `Any2Odyssey-<version>-windows-x64.zip` with the executable and the installer scripts, and from 0.9.4 the setup program `Any2Odyssey-<version>-windows-x64-setup.exe`, which carries the files of that ZIP and runs the same installer (`installer/README.md`).
- Linux x86_64, from 0.9.0, two files per release (built by the release workflow, each with a `.sha256`): `any2odyssey-<version>-1-x86_64.pkg.tar.zst` for Arch-based distributions (Arch, CachyOS, EndeavourOS, Manjaro; `sudo pacman -U <file>`), built in an Arch Linux container, and `Any2Odyssey-<version>-linux-x86_64.tar.gz` for others, built on Ubuntu 24.04 (it needs glibc 2.35 or newer and PipeWire; `INSTALL.txt` inside says the rest). The archive has an installer, `install.sh` (`packaging/linux/install.sh`): the program for the user under `~/.local`, then, asking first, the packages it needs (Arch, Debian/Ubuntu, Fedora and openSUSE names; run on CachyOS and, without an Odyssey 3D, on the distributions named below; a package the release does not have is named and left out), the udev rules, the depth model and the Wine side of the Odyssey 3D; `--uninstall` removes it. For the Wine side it uses a Windows drive it finds by itself only when exactly one is mounted and it is not a removable one (with `--yes`, only when it is plainly a drive inside the machine); Windows on a USB drive, a memory card or a network share, or one of several, is named with `--windows-root DIR`. The package installs the udev rules itself and has the same further steps as `any2odyssey-setup`. After an update the Odyssey 3D step is run again, because the Wine side stays as the earlier version built it until then. Releases later than 0.9.0 also carry build provenance for every published file, the Windows ones included: four from 0.9.4 on, three before it (`gh attestation verify <file> -R jlobue10/Any2Odyssey`). Both carry the Wine setup for the Odyssey 3D (`wine-lens`; in the package under `/usr/share/any2odyssey/`) and the licenses of what they contain (`THIRD-PARTY-LICENSES.md`, `THIRD-PARTY-LICENSES-LINUX.md`). Neither published file has been installed and run by a person yet: what was run on hardware is a build from the same source. The package can also be built from a checkout:

  ```sh
  git clone https://github.com/jlobue10/Any2Odyssey.git
  cd Any2Odyssey/packaging/arch
  makepkg -si
  ```

  This installs `/usr/bin/any2odyssey`, a desktop entry (it appears as an "Open with" choice for PNG, JPEG and BMP images), the icon, the guide and the license files. `zenity` or `kdialog` provides the Open and Save dialogs; without either, type the path or drop the file on the window. Other distributions: `cargo build --release -p any2odyssey` and run `target/release/Any2Odyssey`.
- Building the Linux edition needs the PipeWire development files and clang (the live capture's bindings are generated from PipeWire's headers); the package depends on `libpipewire`.
- The CI builds and tests the core, the icon tool and the application crate on x86_64 and aarch64 Linux, and builds the Arch package in an Arch Linux container.

## What has been run on Linux

The stereo viewer was built and run on Arch Linux under WSL 2 (x86_64) with the package above: X11 under a virtual display with the Openbox window manager, software OpenGL. Checked there: opening an image by argument and by hand-over from a second launch, the anaglyph preview, the refusal of an odd-width pair, the output window, full screen and Esc, `--show` and `--quit`. The 2D → 3D mode was run there too, on the CPU provider of `onnxruntime-cpu` 1.29 with the downloaded model: a photograph converted to an anaglyph with the expected parallax, and the missing-model message without it. On a CachyOS desktop (x86_64, KDE Wayland, NVIDIA RTX 5090) with a G90XF, the lens switch, Leia's eye tracker, the weaver helper and AI depth on the GPU (`onnxruntime-cuda`) were run as described in `docs/LENS-SWITCH.md`. On the same machine the Odyssey 3D output was seen from the viewer on the panel: a still image with AI depth (upright, depth the right way round, following the viewer), and the live screen with the Odyssey's own desktop as the screen on KDE Plasma 6.8, including video playing. Known there: the desktop's real pointer, drawn flat over the 3D picture, looked doubled through the lens early in that session and looked right by its end, after the eye tracking's timing had been corrected (nothing was changed for the pointer itself); some flicker while the head moves remained after the camera's time stamps were corrected (which reduced it); the repeated stop and start and the 2160-line detail were fixed afterwards and checked by measurement only. **Not yet run:** the rest of the viewer on a physical Linux desktop, the zenity/kdialog dialogs, drag and drop, more than one display, and aarch64 beyond CI's build and tests.

The viewer was also run under a Wayland compositor without a screen (sway 1.12 with two headless outputs, software OpenGL, in the same WSL 2 installation; start-up on weston 15 as well). Checked there: it starts as a Wayland client whenever `WAYLAND_DISPLAY` names a compositor, with or without XWayland beside it, and under XWayland alone as an X11 client; the compositor reports the application id `any2odyssey` (the desktop entry's name, so the desktop finds the icon and groups the windows) for the controls and the output window; the picture is sharp at output scales 1.5 and 2; the output window goes full screen on the output it is on, comes back to the other output when its own is unplugged, and leaves full screen with F11, a double click or Esc; 200 hand-overs (`--show`, `--toggle`, `--open`) arrive while the controls are on another workspace; zenity opens as a Wayland window; when the compositor dies the program exits 1 at once. A live screen without a session bus, or with a portal that has no screen cast, ends with the reason on the page. What Wayland does not let a window do: `--show` cannot raise or restore the controls (they ask for attention instead, which the desktop shows in its task bar), a window cannot place itself on a display (the output window is moved there by hand, as its hint says, or by a window rule of the desktop), and a window icon comes from the desktop entry only. On a compositor without server-side decorations (GNOME) the output window gets the windowing library's plain title bar: a dark bar without the window's name, with buttons to minimize, maximize and close, and edges to resize by (the desktop's own Super + drag moves it too). **Not run under Wayland:** drag and drop, a hardware GPU, and anything of the Odyssey 3D output, whose window belongs to Wine.

The viewer and the live screen were then run on the two desktops most people have, each without a screen in the same WSL 2 installation (Arch, software OpenGL, a stand-in for the Wine side, the controls driven through the accessibility bus and through each compositor's own way in for a pointer and a keyboard): KDE Plasma 6.8 (`kwin_wayland --virtual` 6.8.2 with two outputs, xdg-desktop-portal-kde 6.8.2) and GNOME 51 (`gnome-shell --headless` with two virtual monitors, mutter 51.1, xdg-desktop-portal-gnome 51.0), both with PipeWire 1.6.11, WirePlumber 0.5.19 and xdg-desktop-portal 1.22.1, as a Wayland client and as an X11 client through Xwayland. What that showed:

- **The live screen.** Both desktops ask once which screen to share and remember it, over a new start of the program too; both send 8-bit BGRx in ordinary memory (neither offered a DMA-BUF without a GPU, so that path was not seen). A still screen, a changing one, Stop, Start and `--quit` while live behave as on sway. A screen switched off, the portal's backend ended, and PipeWire ended each end the cast with "the screen cast was ended by the desktop", and Start works again; a WirePlumber that is away is called a pause and the picture comes back by itself. On GNOME a monitor that is taken away ends the cast the same way, and so does a change of the shown monitor's scale or a quarter turn of it: mutter ends the cast there, and Start shows the screen again in its new shape (a mirrored monitor is shown on without a break). On KDE a change of rotation, scale or mode leaves the cast running at the size it had, so a screen turned while it is shown is pressed into the old shape until the output is stopped and started.
- **A turned screen** comes upright from both desktops, as a frame of the turned size (1080 x 1920 for a 1920 x 1080 screen on its side). Neither sends the note that says how a frame is turned (`SPA_META_VideoTransform`), which sway and other wlroots desktops send with a frame that is not turned.
- **The size of the cast on KDE** is what the reader wishes for: KWin offers every size from 200 x 200 to 10000 x 10000 and resizes the picture. The program wishes for none, and gets the screen's own.
- **The pointer in the picture** was seen on GNOME (drawn when asked for, absent when not). KWin draws no pointer on an output that has no screen, so it could not be seen there.
- **The windows.** The controls are moved by their title bar, resized by their edges, maximized by the button and by a double click, minimized and closed on both desktops (on GNOME the double click could not be made by the rig). The output window has KWin's title bar on Plasma and the plain one described above on GNOME; F11 makes it full screen on the monitor it is on and Esc leaves, also while the controls are minimized. `--show` from a second launch: as a Wayland client the controls ask for attention (KWin restored and focused them when they were minimized; GNOME left them minimized and marked them), as an X11 client they are raised and focused on both.
- **The file dialogs.** With zenity installed, on Plasma the dialog that opens is KDE's own (zenity asks the portal for it); without zenity, kdialog. On GNOME zenity's dialog is the Files program's, which does not run for root, so the rig showed zenity's own instead. A picture was opened and a preview saved through each, and a dialog left open went away with the program.
- **The KWin script** of the Odyssey 3D set-up (`contrib/wine-lens/tools/kwin-overlay.js`) was loaded into KWin 6.8.2 the way `any2odyssey-weaver` loads it, with a plain window of the Wine program's class standing in for it: the window is left out of the screen cast and of KWin's screenshots, stays above a window that is made active over it, and windows of that class that appear later are found.

The desktops and sessions that were left were run the same way after 0.9.8 (the same WSL 2 installation, software rendering only, a stand-in for the Wine side, the controls driven through the accessibility bus): labwc 0.20.2 (wlroots 0.20, two headless outputs, xdg-desktop-portal-wlr 0.8.4); COSMIC (cosmic-comp 1.11.0, xdg-desktop-portal-cosmic 1.11.0) and niri 26.04 (xdg-desktop-portal-gnome 51.0), each as a window of a headless sway, because neither starts without a screen; and X11 sessions under Xvfb with xfwm4 4.20 and with i3 4.25, with the GTK portal backend alone, with GNOME's, with KDE's, with no portal and with no session bus. Two could not be started without a graphics card: Hyprland 0.57.2 ("Cannot open backend: no allocator available") and gamescope 3.17.0 (its headless and its nested mode both need more of Vulkan than the software renderer has). What that showed:

- **Where there is no screen cast** the page says so within 0.6 s of Start, and nothing hangs: in an X11 session with the GTK backend alone ("this desktop's portal cannot share a screen ..."), with GNOME's or KDE's backend under X11 (they answer without a reason, and the page says what such a backend needs), with no portal installed and with no session bus. GNOME and KDE no longer have an X11 session of their own, so no X11 session that was run had a screen cast.
- **labwc** behaves as sway does: 8-bit BGRx in ordinary memory, 17 to 19 pictures a second of a terminal that changes 20 times a second, "not changing" eight seconds after it stops, a turned, mirrored or scaled output shown upright and equal to the compositor's own screenshot (all of 90, 180, 270, flipped, flipped-90 and scales 1.25, 1.5 and 2; the page names 1080 × 1920 for an output on its side), a change of mode followed while live, and the cast ended with its line when the output is switched off, the portal's backend ends or PipeWire ends. xdg-desktop-portal-wlr's own chooser was not run: the rig named the output in its configuration, and there is then no dialog at any Start. The pointer is part of every frame of a headless output, wanted or not, so that choice could not be seen.
- **COSMIC** asks once ("Share your screen", the screens as pictures) and remembers the screen, over a new start of the program too; it sends 8-bit RGBA in ordinary memory with the note that says how the frame lies, and the picture equals COSMIC's own screenshot, upright; an output turned while live is followed at once (the page names 1080 × 1920). A change of scale ended the cast, and Start showed the screen again. Started from a terminal, the program has no name the portal knows, and COSMIC's dialog then names another program ("KWin Dialog Helper" on the rig). In this nested session the portal backend of 1.11.0 ended most casts by itself, two seconds to a minute after they began, some with a protocol error of its own, and for another reader of the cast as well; the page then reads "the screen cast was ended by the desktop" and Start works without a dialog. What the page says of a still screen could not be seen for that reason; a changing one came at 24 to 31 pictures a second.
- **niri** shows GNOME's "Share Screen" dialog with the displays only and "Remember this selection". As a window of another compositor it cannot cast ("no GBM device available"), and it closes the portal session without an answer: the page says that the desktop gave up the screen cast before it had started (up to 0.9.8 it went on asking for a choice in a dialog that was gone). Nothing more of the live screen could be run on niri. Started without `--session`, niri offers no screen cast at all, and the page says that the portal gave no reason.
- **Hyprland's portal backend** (xdg-desktop-portal-hyprland 1.5.0) was run on labwc, as far as it goes there: it shows its picker when the sources are chosen, not at Start; its picker leaves at once where Hyprland is not running, and the page reads "no screen was chosen" (up to 0.9.8: "Invalid session"). With a stand-in picker the backend never sent a picture there, to any reader. Hyprland itself was not run.
- **The 3D picture on the shown screen.** Nothing but KWin keeps the Wine window out of a cast: on labwc a window of the Wine program's class, full screen on the shown output, was the whole of the picture that was shown. `any2odyssey-weaver` now reports that on every desktop without KWin, and the page says for as long as the screen shows: "This desktop cannot keep the 3D picture out of a capture: do not show the Odyssey's own screen."
- **The windows.** The controls have their own title bar everywhere and no second one from the desktop (xfwm4, i3, labwc, niri, COSMIC); under X11 the window cannot be made smaller than 700 × 360 by the window manager. Maximize and Minimize by the buttons work on xfwm4 and labwc, Maximize on COSMIC (what Minimize did there the rig could not read); on i3 and niri, which have no such states, they do nothing. `--show` from a second launch restores and focuses minimized controls under xfwm4; on labwc they stay minimized (see above for Wayland), and labwc has no task bar of its own to find them in. Close ends the program everywhere (exit 0). The output window gets the desktop's title bar on xfwm4, i3, labwc and COSMIC, and on niri, set to draw none, it is a bare tile; F11 makes it full screen on the output it is on (labwc: the second of two) and Esc leaves, then closes it.
- **The file dialogs.** With zenity, the dialog is GTK's own under X11, the GTK portal's on labwc and COSMIC's own on COSMIC. In all three zenity's save dialog opened at the root of the file system for a bare file name; the program now names the current folder, and it opens there. kdialog opened and saved under xfwm4 and on labwc. Without either, the page says that no file dialog is installed.
- **Not run:** Hyprland and gamescope themselves, a cast as DMA-BUF, ten bits a colour (labwc has no setting for it), the pointer in the picture, drag and drop, and anything on real hardware.

## Why Samsung's engine cannot be used on Linux

Conversion is done by Samsung's `ConversionWrapper.dll` (CUDA/ONNX, Windows x64) and the calibrated glasses-free output needs the LeiaSR runtime, eye tracking from the monitor's camera and the lens calibration. The conversion engine does not exist for Linux, and Leia's SR runtime for Linux is a commercial package that is not public. Running Samsung's conversion engine under Wine/Proton is unvalidated and outside this project's scope. Leia's runtime is asked to switch the lens on, either by its Linux package where that is installed or by its Windows service running under Wine (`docs/LENS-SWITCH.md`); its eye tracker and weaver run under Wine as well, from the user's own copy, and the viewer's Odyssey 3D output uses them. Any2Odyssey's Linux edition is therefore the stereo viewer described above, with depth from an open model.

## Development machines

The maintainer develops on an aarch64 Linux laptop (cross-checks the Windows code with `cargo check --target x86_64-pc-windows-msvc`) and tests the Windows converter on an x64 Windows PC with a G90XF. Hardware results are recorded in `CHANGELOG.md` and `docs/TESTING.md`.
